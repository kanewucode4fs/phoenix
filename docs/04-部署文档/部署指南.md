# 部署指南

> 对应源码：`4de0e4f88`，Phoenix `20.23.0`；核对日期：2026-10-16。
> 阅读导航：[业务架构](../02-业务架构/业务架构.md) · [技术架构](../03-技术架构/架构详解.md)。以下区分本地开发、容器和 Kubernetes。示例凭证均为占位符，执行前必须替换，并放入受保护且被忽略的环境文件或密钥系统。

## 1. 部署形态与前置条件

| 形态 | 运行组成 | 用途与限制 |
|---|---|---|
| 本地源码开发 | uv Python 环境 + React/Vite；全量开发还使用 dekit | 修改代码、调试、运行测试；不是生产前端服务方案 |
| Python 包/源码构建后启动 | Phoenix 服务 + 已构建静态 UI + SQLite/外部 PostgreSQL | UI/API 同源；没有 UI 构建产物时只启动后端不能证明页面可用 |
| 单容器 SQLite | Phoenix 镜像 + 持久卷 | 本地试用、单节点；写入串行、需保护数据库文件 |
| 根 Compose | 本地构建 Phoenix 镜像 + PostgreSQL 16 + 数据卷 | 仓库现成的开发/验证部署；默认凭证与未开启认证不适合直接公网暴露 |
| Helm | Phoenix Deployment + 可选 PostgreSQL、PVC、Service、Ingress | 更完整的 Kubernetes 配置入口；需要实际集群、存储类和受控密钥 |
| Kustomize | Phoenix/PostgreSQL StatefulSet 和认证 patch | 仓库示例存在需修正项，见第 7 节 |
| Render | 官方镜像 + Render 管理 PostgreSQL | [render.yaml](../../render.yaml)；远程资源及费用需单独配置，本指南不实际创建 |

### 本地工具要求

- Python 包支持 `>=3.11,<3.15`；`.python-version` 和 `make install-python` 选择 3.11，使用 uv 管理的解释器。
- uv 约束 `>=0.12.19,<0.13`；Makefile 通过 `scripts/uv.sh` 使用 0.12.19，必要时由 uv tool 隔离获取该版本，不替换系统 Python。
- Node.js `>=24.20.0`；JS workspace 的 packageManager 为 `pnpm@12.0.0`。
- `make dev` 还依赖 `dekit`；`ensure:dekit` 会检查并在缺失时退出，`make setup` 不负责安装它。
- `make setup` 的 `check-tools` 还检查 `tox`；使用项目兼容的隔离工具环境准备它，不向系统 Python 全局安装依赖。
- 容器方式需 Docker 与 Compose；Helm 方式需 Helm、kubectl、可达集群及 chart 依赖下载网络。
- LLM 评估、PXI、外部沙箱只有在启用时才需要模型/沙箱凭证；仅查看已有数据不需要模型调用。

版本与命令来源：[pyproject.toml](../../pyproject.toml)、[JS workspace](../../js/package.json)、[前端 scripts](../../js/app/package.json)、[Makefile](../../Makefile)。

## 2. 端口、数据与环境变量

| 端口 | 服务 | 默认行为 |
|---|---|---|
| `6006` | UI、REST、GraphQL、OTLP HTTP、MCP | 主 HTTP 服务；`PHOENIX_PORT` 可更改 |
| `4317` | OTLP gRPC | `PHOENIX_GRPC_PORT` 可更改；跨网使用时还需配置网络和 TLS |
| `9090` | Prometheus `/metrics` | 必须显式启用；声明 EXPOSE 不代表指标已启动 |
| `5173` | Vite 开发服务器 | `VITE_PORT` 控制；不用于生产部署 |
| `5678` | 开发 debugpy | 前端开发脚本默认监听，生产不开放 |
| `5432` | PostgreSQL | 服务间数据库连接端口；不必对外公开 |

### 2.1 主要服务端配置

| 环境变量 | 源码默认/约束 | 作用 |
|---|---|---|
| `PHOENIX_HOST` | `0.0.0.0`；Helm 默认 `::` | 监听地址 |
| `PHOENIX_PORT` | `6006`，整数 | HTTP 端口 |
| `PHOENIX_GRPC_PORT` | `4317`，整数 | gRPC 端口 |
| `PHOENIX_WORKING_DIR` | `~/.phoenix`，由 `get_working_dir()` 解析 | SQLite 与本地工作数据位置；部署时建议显式设置并持久化 |
| `PHOENIX_SQL_DATABASE_URL` | 未设置时尝试 PostgreSQL 分项配置，否则 `<working_dir>/phoenix.db` | 主库连接串；支持 PostgreSQL/SQLite |
| `PHOENIX_SQL_DATABASE_SCHEMA` | 未设置；SQLite 忽略 | PostgreSQL schema |
| `PHOENIX_SQL_DATABASE_READ_REPLICA_URL` | 未设置 | 可选读副本连接 |
| `PHOENIX_ENABLE_AUTH` | 服务端默认 `False`；Helm 默认 `true` | 开启认证 |
| `PHOENIX_SECRET` | 开启认证时必需；至少 32 字符，含数字和小写字母 | token 与敏感配置加密根密钥，必须稳定保存 |
| `PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD` | 有内置初始值 | 覆盖首次创建管理员密码；生产设置自己的值 |
| `PHOENIX_USE_SECURE_COOKIES` | `False` | HTTPS 部署设 `True`，纯 HTTP 本地不要盲目开启 |
| `PHOENIX_HOST_ROOT_PATH` | 空；非空时以 `/` 开头且不以 `/` 结尾 | 反向代理子路径，例如 `/phoenix` |
| `PHOENIX_ROOT_URL` | 可选公网地址 | 供回调/客户端访问使用的外部 URL |
| `PHOENIX_ENABLE_PROMETHEUS` | `False` | 开启 9090 指标服务 |
| `PHOENIX_MAX_SPANS_QUEUE_SIZE` | `20000`，正整数 | 摄入队列保护阈值，非严格逐条硬上限 |
| `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS` | `0`，非负整数 | 默认 trace 保留天数；0 表示不按默认天数自动清理 |
| `PHOENIX_LOG_SQL` | `False` | SQL 调试日志 |
| `PHOENIX_ALLOW_EXTERNAL_RESOURCES` | `True` | 控制服务主动获取公共资源，不封锁显式配置的模型/沙箱 |
| `PHOENIX_TELEMETRY_ENABLED` | `True`；禁止公共资源时关闭 | 产品遥测总开关，和应用 OTLP 追踪采集不同 |
| `PHOENIX_ENABLE_MCP_SERVER` | `True` | 挂载 `/mcp` |
| `PHOENIX_ENABLE_MCP_CODE_MODE` | `True` | 外部 MCP 的代码模式 |
| `PHOENIX_DISABLE_AGENT_ASSISTANT` | `False` | 部署时禁用 PXI；也有运行时管理开关 |
| `PHOENIX_ALLOWED_SANDBOX_PROVIDERS` | 未设置时允许全部类型；`NONE` 全禁用 | 代码评估沙箱允许列表 |
| `PHOENIX_SKILLS_PATHS` | 空，逗号分隔目录 | 服务器启动时加载外部技能，建议用绝对路径 |

完整配置（含 SMTP、OIDC、LDAP、TLS、数据库存储保护和 Agent 专用配置）以 [config.py](../../src/phoenix/config.py) 与 [Helm values](../../helm/values.yaml) 为准。默认配置差异很大，不能拿 Helm 的认证默认值推断直接启动 Python 的行为。

### 2.2 客户端与凭证

外部应用、CLI 和评测执行器使用 `PHOENIX_COLLECTOR_ENDPOINT` 指向 Phoenix，并在开启认证时配置 `PHOENIX_API_KEY=<your-key-here>`。不要把服务端监听变量 `PHOENIX_HOST` 当作跨进程客户端地址配置。

模型供应商、托管沙箱、GitHub、SMTP 等凭证按需配置，不与 Phoenix API key 混用。使用 UI 保存凭证时，也需要妥善保管 `PHOENIX_SECRET`。更新这个 secret 可能导致已有加密配置不可解密，不能每次启动随机更换。

## 3. 本地开发与构建

在仓库根执行：

```bash
make help
make setup
make dev
```

`make setup` 检查基础工具，安装 Python 依赖和 JS workspace 依赖，并构建 UI 所需 workspace 包。`make dev` 进入 `js/app`，通过 dekit 启动 API、Vite 和示例数据生成任务，工作流见 [dekit.yaml](../../js/app/dekit.yaml)。

全量开发脚本会补建缺失的 `js/app/.env`，并将 `PHOENIX_TELEMETRY_ENABLED=False` 写入该文件；已有文件保留。脚本使用 shell source 读取环境文件。自行创建环境文件时只存本地配置，真实凭证不得进 Git。

不使用 dekit 时，可在完成环境文件准备后用两个终端运行已有目标：

```bash
# 终端一：API
make dev-backend
```

```bash
# 终端二：Vite
make dev-frontend
```

`dev-backend` 不会 source `js/app/.env`，且只有 `--debug`，没有 `--dev`；需要的环境变量应在启动该终端时显式提供。拆分目标可用于分别调试 API/Vite，但不能把它视为与 `make dev` 完全相同的 UI 热加载方案。需要后端引用 Vite 资源时使用 `make dev` 中带 `--dev` 的 API 脚本；只运行 `dev-backend` 查看 UI 则须先具备静态构建产物。全量开发以 Phoenix HTTP 地址 `http://localhost:6006` 为主要入口。

构建与检查：

```bash
make build-frontend
make build-python
make typecheck
make test-python
make test-ts
```

若准备发行包含 UI 的 Python 包，先构建 frontend 再构建 Python。前端构建输出到 `src/phoenix/server/static/`。`make build` 是聚合目标，勿擅自以并行构建替代需要的前后顺序。测试需要项目依赖与相应测试服务，本指南不把命令存在视为已经验证通过。

## 4. 容器部署

仓库没有生产镜像构建的独立 Make 目标；使用原生 Docker 命令。`make dev-docker` 对应 `scripts/docker/devops` 的开发环境，并非根目录 Compose。

### 4.1 本地镜像和 SQLite 持久化

```bash
docker build -t phoenix:local .
docker volume create phoenix-data
# 首次创建空卷时，赋予最终镜像 nonroot 用户写权限
docker run --rm --user 0:0 --entrypoint /usr/bin/python3 \
  --mount source=phoenix-data,target=/data \
  phoenix:local -c "import os; os.chown('/data', 65532, 65532)"
docker run --detach --name phoenix-local \
  --publish 127.0.0.1:6006:6006 \
  --publish 127.0.0.1:4317:4317 \
  --env PHOENIX_WORKING_DIR=/data \
  --env PHOENIX_TELEMETRY_ENABLED=False \
  --mount source=phoenix-data,target=/data \
  phoenix:local
```

这是仅绑定本机的试用方式，未开启认证。镜像以 nonroot 用户运行；用宿主目录代替 named volume 时，目录需要允许容器 UID 写入。需要对其他机器提供服务时，先按第 5 节配置认证和网络边界。

镜像分阶段构建 React、Python 和本地沙箱 runtime，最终为 distroless 镜像，包含 Deno 及 CPython WASM。默认不带普通 shell；不要把 `docker exec ... sh` 作为标准排障步骤。WASM binary 通过 `PHOENIX_WASM_BINARY_PATH` 指向镜像内文件。

### 4.2 根目录 Compose

```bash
docker compose config --quiet
docker compose up --detach --build
docker compose ps
docker compose logs --tail=100 phoenix
```

根 [docker-compose.yml](../../docker-compose.yml) 构建 Phoenix，并依赖 PostgreSQL 16；Phoenix 暴露 6006/4317，数据库保存在 `database_data` named volume。数据库端口声明 `5432`，不是固定映射宿主 5432，实际端口用 `docker compose port db 5432` 查询。

该文件使用本地演示凭证，未启用认证；`depends_on` 只表示启动顺序，没有数据库健康等待条件。若首次 Phoenix 启动时数据库尚未就绪，应先查看 db 日志、确认 ready，再重新启动 Phoenix 服务。

生产部署应使用自己的覆盖文件或受管配置，统一数据库用户/密码、连接串、secret 和认证；不要把根 Compose 原样发布到公网。不要执行 `docker compose down --volumes` 来排障，它会移除数据库卷。

## 5. 认证、代理与持久化配置

### 5.1 生产环境变量示意

```dotenv
PHOENIX_WORKING_DIR=/data
PHOENIX_SQL_DATABASE_URL=postgresql://phoenix:<your-password-here>@db:5432/phoenix
PHOENIX_ENABLE_AUTH=True
PHOENIX_SECRET=<your-32-plus-character-secret-with-lowercase-and-digit-here>
PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD=<your-initial-password-here>
PHOENIX_TELEMETRY_ENABLED=False
```

该片段是字段示意，包含占位符，不能直接当作已可启动的环境文件。通过密码管理器或 Secret 注入真实值；数据库密码中的 URL 保留字符须正确编码。初始管理员邮箱见 `src/phoenix/auth.py`（`admin@localhost`），首次登录按产品要求设置新密码。

对外 HTTPS 由反向代理终止时，配置可信来源、外部 URL 与安全 Cookie；直连 TLS 可使用 `PHOENIX_TLS_ENABLED_FOR_HTTP`、`PHOENIX_TLS_ENABLED_FOR_GRPC` 及证书相关配置。HTTP 与 gRPC 的代理转发方式不同，映射 HTTP 端口不会自动提供 OTLP gRPC。

### 5.2 子路径与来源

服务发布在 `https://<your-host-here>/phoenix` 时，`PHOENIX_HOST_ROOT_PATH=/phoenix`；代理与客户端地址必须与此一致。该值不能以 `/` 结尾。前端构建使用相对资源路径，后端负责入口资源及 router basename。

OIDC 回调、OAuth 授权、MCP、CSRF 与跨域来源须根据实际公网 origin 配置。不要用宽泛 CORS 规则代替检查代理转发、Cookie 和回调 URL。配置证据见 [config.py](../../src/phoenix/config.py)、[Vite](../../js/app/vite.config.mts)、[app.py](../../src/phoenix/server/app.py)。

### 5.3 数据与密钥备份

- SQLite：持久化整个工作目录，使用数据库一致性备份方法；活跃 WAL 数据库不能只随意复制一个 `phoenix.db` 文件。
- PostgreSQL：备份数据库和恢复所需配置；执行升级前先做可恢复备份。
- 保存 `PHOENIX_SECRET`、外部 Secret 引用及供应商配置；只备份数据库而丢失 secret 可能无法恢复已加密凭证。
- trace retention 与临时实验/助手清理可能删除数据；备份计划与业务保留期应分别配置。

## 6. Helm 部署

本地 chart：`helm/`；chart 版本 `12.0.23`，appVersion `20.23.0`，默认镜像 tag 为 `version-20.23.0-nonroot`。

```bash
helm dependency build ./helm
helm lint ./helm
helm template phoenix ./helm --namespace phoenix --values /absolute/path/to/phoenix-values.yaml
helm upgrade --install phoenix ./helm \
  --namespace phoenix --create-namespace \
  --values /absolute/path/to/phoenix-values.yaml
kubectl --namespace phoenix get pods,services
```

values 文件需先按实际环境准备，上面不是零配置生产安装。默认启用内置 PostgreSQL、认证和 Ingress，Service 类型为 NodePort。chart 默认 PostgreSQL 凭证属于示例值，部署时应覆盖。

| 存储方案 | `persistence.enabled` | `postgresql.enabled` | `database.url` |
|---|---|---|---|
| SQLite + PVC | `true` | `false` | 空，由工作目录自动生成 |
| chart 内置 PostgreSQL | `false` | `true` | 空 |
| 外部 PostgreSQL | `false` | `false` | 外部 URL；或使用 postgres 分项配置 |
| 内存 SQLite（临时演示） | 依配置 | `false` | `sqlite:///:memory:` 或 `persistence.inMemory` |

内存模式重启丢数据。chart 校验会拒绝冲突的存储方案；不能同时打开 SQLite PVC 和内置 PostgreSQL，也不能同时配 database.url 与相互冲突的分项连接参数。内置 PostgreSQL 的凭证需与 Phoenix 消费的 Secret 保持一致。

`auth.createSecret`/`auth.name` 及 `auth.secret[]` 控制凭证注入；可引用已有 Secret。主 secret 自动生成的生命周期、升级时保留和备份必须按实际 Secret 模板核对。默认应用资源 requests 为 500m/1Gi，limits 为 1000m/2Gi，是 chart 配置值，不是容量保证。

探针：liveness/startup 请求 `/healthz`，readiness 请求 `/readyz`。示例转发 UI/API：

```bash
kubectl --namespace phoenix get services
# 将服务名替换为上一条命令列出的 Phoenix Service
kubectl --namespace phoenix port-forward 'service/<your-phoenix-service-here>' 6006:6006
```

镜像调试、read-only filesystem、挂载、工作目录写权限及沙箱运行条件应一并核实。默认允许 Docker sandbox 不代表 Kubernetes 容器中有 Docker daemon；不要为消除报错直接挂载宿主 Docker socket。

## 7. Kustomize 与 Render 的适用边界

[kustomize/base](../../kustomize/base) 的 PostgreSQL `POSTGRES_DB` 为 `postgresdb`，Phoenix 连接 URL 的库名为 `postgres`。正式使用前应把两处统一为同一个实际数据库；本文记录差异，不修改部署资产。

[认证 patch](../../kustomize/auth/patches.yaml) 含固定示例 secret，必须改成自己的 Kubernetes Secret 引用。不要复用示例 secret。base 中 readinessProbe 没有使用本指南建议的 `/readyz`，应在自己的 overlay 中明确配置数据库就绪检查。

可以先做本地渲染检查，完成 overlay 修正后再决定是否应用集群：

```bash
kubectl kustomize kustomize/base
```

[render.yaml](../../render.yaml) 使用官方 `latest` 镜像、管理 PostgreSQL、自动生成认证 secret，并启用 secure cookies。需要可复现版本时应在自己的蓝图中固定镜像；Render 的 `/healthz` 检查不代表数据库读写路径已验证。

## 8. 在线回评、Agent 和 Skill 执行环境

Phoenix 主服务不自动执行所有在线回评。PXI 定时回评由 [.github/workflows/pxi-online-evals.yml](../../.github/workflows/pxi-online-evals.yml) 执行，要求能访问目标 Phoenix、具有写入注解的凭证，并在启用 LLM judge 时配置对应供应商 key。

本地预览执行器（只读 dry-run，使用现有项目环境）：

```bash
PHOENIX_PROJECT=pxi_dev ./scripts/uv.sh run python -m evals.pxi.online_evals.run --dry-run
```

默认项目和 evaluator 面向 PXI，不能直接把任意线上项目切过去就认为评测口径成立。模型凭证在执行器环境中配置，与服务器内部保存的凭证不是自动互通的。

Harbor 在独立环境执行任务；当前 Makefile 为其固定兼容的 Python 版本并准备 Phoenix/client/CLI 产物。使用 `make harbor-stage`、`make harbor-run` 前先阅读 [Harbor README](../../evals/harbor/README.md) 并选定 job、Agent、模型和基础设施。运行可能调用付费模型或创建沙箱，本次文档生成不执行这些操作。

## 9. 启动后的验证

### 9.1 进程与数据库

```bash
curl --fail --silent --show-error http://localhost:6006/healthz
curl --fail --silent --show-error http://localhost:6006/readyz
curl --fail --silent --show-error http://localhost:6006/arize_phoenix_version
```

预期分别为 `OK`、JSON 对象、服务版本。配置子路径或 TLS 时替换 URL。`/readyz` 失败通常表明数据库访问未成功；`/healthz` 成功不能替代它。

### 9.2 业务与持久化

1. 访问 UI；开启认证时验证登录与当前角色，检查数据集/追踪页面能读取数据。
2. 用实际应用发送一条追踪，确认目标项目能查到完整 span；另行核对 HTTP/gRPC 所用协议。
3. 运行一个小型实验，检查 task 输出、评估结果及错误；启用代码评估器时单独验证所选沙箱。
4. 重启服务后确认测试数据仍存在，核实实际连接的数据库和卷，而非仅检查容器状态。
5. 启用指标时检查 `http://localhost:9090/metrics`；指标端口需单独映射与访问控制。

这些是部署验收步骤，不是本轮实测记录。没有模型/沙箱凭证时，相应能力应标为未验证。

## 10. 日志、排障与升级回退

| 现象 | 优先核查 |
|---|---|
| `make dev` 报 dekit 不存在 | 前端 `ensure:dekit` 检查；准备工具，或使用拆分开发目标 |
| 页面空白/静态资源 404 | 是否先构建 frontend；static 目录、Vite 状态、子路径和代理映射是否一致 |
| 数据库连接拒绝/库不存在 | PostgreSQL readiness、URL、认证、网络；Kustomize 库名差异 |
| Kubernetes 下 PHOENIX_PORT 不是整数 | 同名 Service 自动注入的 `tcp://...` 变量；显式配置数值端口 |
| 登录后仍未认证 | secure cookie 与 HTTPS、跨域 origin、代理公网 URL、token audience/过期 |
| 评估失败而追踪正常 | evaluator 输入映射、模型凭证、配额、任务错误、沙箱 runtime 与网络 |
| span 摄入被拒绝或延迟 | 队列容量、磁盘空间保护、DB 写入吞吐、认证角色、客户端重试 |
| 凭证无法解密 | 部署后是否更换 PHOENIX_SECRET；恢复原 secret，核对数据库来源 |
| 重启后数据消失 | 是否使用内存库、卷未挂载、工作目录变化或连接到了另一数据库 |
| 9090 无响应 | 是否启用 Prometheus 且映射端口；EXPOSE 本身不启动服务 |

日志从进程 stdout、`docker compose logs` 或 `kubectl logs` 获取。dekit 的 API 任务额外 tee 到 `/tmp/phoenix-<端口>.log`。SQL 日志用于受控调试，避免无意扩大敏感数据留存。

升级前保存数据库一致性备份、旧镜像标识和密钥配置，核对 Alembic 变更；多副本部署须规划迁移窗口。失败回退优先使用已验证的旧镜像和兼容数据库；若新迁移不向后兼容，需按已验证的备份恢复方案操作，不能假设直接降级镜像一定可用。不要用删除卷、删除数据库或更换 secret 当作通用恢复手段。
